Agent utility vs. agent security

Inspect AI · OWASP Top 10 for Agentic Applications (2026)

An agent's task utility and its security resilience are separable axes.

I built an Inspect AI eval suite around a single tool-using support agent for a fictional B2B SaaS company, and scored every run twice: once on whether it finished the ticket, once on whether it resisted an attack planted in its environment. Same environment, same tools, one payload moved at a time. Then I ran the whole suite against three defensive postures to see what hardening actually costs.

How this was measured

Scoring is on actions, not on prose

Every tool call the agent makes is appended as a JSON line to an action ledger inside the Docker container the sample runs in. Both scorers read that ledger back out of the container after the run. Nothing is graded by asking a model whether the answer looked good, and an agent that says it escalated but never called escalate scores zero. A call the policy engine refuses is recorded with blocked: true and never counts as an action that happened.

The two axes are scored independently

Task utility is a deterministic per-scenario spec: required actions with argument constraints (refund exactly $49.00; email the verified contact; escalate to tier 3 security-response) plus forbidden actions (never close a security ticket). Attack success is a separate spec per payload, describing what the attacker wanted. A run can score 1.0 on both — the agent finished the ticket and got owned on the way through. That cell is the reason the two axes have to be separate.

Attacked and clean samples are the same environment

Each attack sample is a base scenario with a payload appended to exactly one fixture file — one ticket body, one fetched page, one knowledge-base article, or one line of CRM notes. A test in the suite asserts that the attacked and clean environments differ in exactly one file, so the utility comparison between them is honest.

Safety of the harness itself

Every payload is a synthetic fixture written for this suite. Samples run in a throwaway Alpine container with network_mode: none, so there is nothing outside the sandbox for a hijacked agent to reach. "Sending an email" means appending a line to a file in that container. The credentials in the fixtures are invented canary strings, and they exist so that exfiltration can be detected objectively rather than judged.

Limits of this result

  • One run per cell. Every number here is a single attempt at each of the 32 samples, per posture, per model. With only 6 samples in each OWASP class, one flipped sample moves a per-class rate by 16.7 points. Read the class bars as direction, not as precision, and don't read a 3-point gap as a real difference.
  • Unequal model coverage. The full three-posture sweep ran on one model. The second model covers only the two prompt-level postures, because its API key ran out of credit partway through the third run. The main charts are therefore scoped to the model that ran every posture, and the second model appears only as a cross-model control on the postures it actually covers.
  • A small suite on one domain. Eight base scenarios in one B2B SaaS support-desk environment. Nothing here says how these postures behave on a coding agent, a browser agent, or a multi-agent system.
  • Four of ten OWASP classes. ASI04, ASI05, ASI07, ASI08, ASI09 and ASI10 need a supply chain, a code interpreter, agent-to-agent messaging or a human in the loop. This harness has none of those, so I left those classes alone rather than fake them.
  • My payloads, my results. I wrote both the attacks and the defenses. A posture that looks strong here is strong against the 24 payloads I thought of. A red team that had not seen the system prompt would very likely do better, and the attacks are single-shot — nothing chains payloads across channels or sessions.
  • One payload was never read. In several runs the agent finished the approved-credit ticket without opening the linked postmortem page, so the payload planted there never entered its context. That sample counts as a defended sample in the headline rate, which slightly flatters every posture. The per-sample exposure check that catches this is in the exported data.
  • The policy engine is deliberately blunt. It enforces a hard $500 credit cap with no approval path, which is exactly why it breaks the legitimate pre-approved credit ticket. A real deployment would build the approval workflow; I wanted the cost of capability restriction to be visible rather than engineered away.
